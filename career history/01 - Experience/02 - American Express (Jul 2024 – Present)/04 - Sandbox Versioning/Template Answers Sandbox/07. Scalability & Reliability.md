## Q7. Scalability & Reliability

**How does the sandbox scale across 40+ markets and 30M+ daily transactions?**

Sandbox architecture is stateless on GCP cloud—no persistent state beyond version metadata and configuration artifacts. Sandbox creation (write) is lightweight: create metadata record, initialize Draft state, allocate version ID. Config edits (accumulated in Draft) are stored as deltas, not full rewrites—memory efficient. Simulation jobs are asynchronous and distributed: GCP parallelizes simulation across markets, limiting latency. Rollback is instantaneous: load a prior version from metadata store (no data migration). Scalability emerges from: (a) stateless compute (horizontal scaling), (b) asynchronous simulation, (c) delta storage (reduced payload). **What are the reliability requirements for sandbox versioning?**

Mission-critical. A sandbox bug or outage blocks all CRR changes—customers cannot be onboarded (BRD 12.12 requires CRR rescoring at onboarding). Reliability requirements: (a) 99.99% uptime for sandbox creation/promotion (critical path), (b) simulation must complete within [VERIFY: add SLA, likely <5 minutes] or user-facing timeout, (c) rollback must succeed 100% of the time (no partial rollbacks), (d) version history must be immutable (no data loss), (e) audit trail must be tamper-proof (regulatory requirement).

**How do you handle Simulation Job Failures?**

If simulation fails mid-execution, user sees "Retry" and "Cancel" options. Retry re-executes simulation against the same production data snapshot (ensures reproducibility). Cancel transitions sandbox back to Draft, allowing user to edit and resubmit. Timeout: if simulation exceeds SLA, automatic failure notification. These behaviors are critical: user cannot be blocked indefinitely.

**What is the disaster recovery strategy?**

Sandbox metadata and version history are replicated across [VERIFY: confirm region count, likely 3+] regions with real-time sync. Production data copy for simulation is ephemeral (deleted post-simulation). Recovery: if primary region fails, failover to replica (user sees no outage). Version history is never lost; production data copy can be regenerated. This aligns with GCP's resilience SLAs.

**How do you prevent data corruption during atomic promotion?**

Promotion uses database transactions with isolation level Serializable (prevents phantom reads and race conditions). Before committing Rules + Assets + FA changes: (a) validate schema compliance, (b) validate referential integrity (rules reference valid assets), (c) test rollback scenario (simulate reverting changes). If any validation fails, transaction aborts with clear error. This ensures zero partial promotions.

**How do you handle concurrent user actions (edge cases)?**

Mutual exclusion (Enterprise and Market sandboxes cannot coexist) prevents concurrent edits. Within a sandbox, only one user can edit at a time (pessimistic locking on sandbox record). If user A is editing Rules and user B tries to edit Assets, user B sees "locked by [User A], wait time estimate [X]" message. Upon user A's completion, lock releases. This ensures serial consistency and prevents merge conflicts.
