## Q10. Execution & Delivery

**How is this feature scoped across sprints?**

11 user stories, 50 story points, 5 sprints (26.1.1 through 26.1.5). Story point breakdown: Sprint 26.1.1: Backend APIs + creation UI (8 pts). Sprint 26.1.2: Lifecycle state management + detail view with sub-navigation (9 pts). Sprint 26.1.3: Versioning + simulation workflow + progress tracking (14 pts). Sprint 26.1.4: Two-step approval + atomic promotion (10 pts). Sprint 26.1.5: Rollback + audit trail export (9 pts). This distributes complexity: infrastructure first (Sprint 1), UI scaffolding (Sprint 2), complex workflows (Sprint 3), governance (Sprint 4), recovery (Sprint 5).

**What is your delivery approach, and what are the key milestones?**

Approach: SAFe/PI planning with bi-weekly sprints. Milestones: (a) Sprint 26.1.1 complete: backend APIs ready for QA integration testing, (b) Sprint 26.1.2 complete: analysts can create sandboxes and navigate detail view, (c) Sprint 26.1.3 complete: end-to-end workflow functional (create → edit → submit → simulate → review), (d) Sprint 26.1.4 complete: approval workflow integrated, atomic promotion tested, (e) Sprint 26.1.5 complete: rollback, audit trail export, production-ready. Each milestone gates the next.

**How do you manage technical risk and dependencies?**

Risk 1: GCP API latency. Mitigation: early spike (Sprint 26.1.1) to measure simulation end-to-end latency; if SLA is unmet, escalate to GCP team for query optimization or capacity planning. Risk 2: Atomic promotion failure scenarios. Mitigation: design review with backend team (Sprint 26.1.4 planning); build comprehensive test suite covering rollback scenarios. Risk 3: Approval workflow complexity. Mitigation: low-fidelity prototype (Sprint 26.1.2) with workflows team to validate state transitions and error paths. Risk 4: UI lock contention under high concurrency. Mitigation: load test with [VERIFY: add target user count] concurrent sandbox creators (Sprint 26.1.1); profile pessimistic locking impact.

**How do you handle UAT and go-live?**

UAT: Week 1 of Sprint 26.1.6 (post-delivery). The compliance team executes scripted test cases covering all workflows (create → edit → submit → simulate → approve → promote → rollback). MLRO teams validate approval flows. Duration: 2 weeks. Go-live: soft launch (the compliance team only) for 1 week. Monitor adoption, incident rate, approval cycle time. Hard launch: all markets after no issues in soft phase.

**What is your approach to training and change management?**

Training: (a) recorded walkthrough (5 min): creation, editing, submission workflow, (b) recorded walkthrough (5 min): approval workflow, (c) in-person office hours (2 sessions: morning/evening to accommodate time zones across 40+ markets), (d) FAQ document (troubleshooting common issues). Roll out training 1 week before soft launch. Change management: communicate via email + in-app notification. Message: "Starting [date], all CRR changes flow through Sandbox Versioning. This new workflow gives you testing, approval audit, and rollback capability—safer and faster than before."

**How do you measure delivery quality (bug escape rate, defect density)?**

Quality gates: (a) code review pass rate 100% (all PR reviews completed before merge), (b) unit test coverage >80%, (c) integration test pass rate 100%, (d) UAT pass rate 100% (zero issues in final UAT), (e) zero critical/high severity bugs post-launch within first 2 weeks. Defect tracking: Rally backlog, prioritized by severity. Post-launch monitoring: track incident rate vs. baseline (expect near-zero incident rate). If incidents surface, root cause analysis and rapid fixes.
