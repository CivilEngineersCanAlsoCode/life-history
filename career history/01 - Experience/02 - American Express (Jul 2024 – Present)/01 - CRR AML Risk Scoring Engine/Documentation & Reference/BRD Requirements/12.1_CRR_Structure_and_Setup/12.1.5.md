# 12.1.5 — Legacy Element Migration

**Parent:** 12.1 CRR Structure and Setup
**Status:** In Development

## Requirement
All the specific elements in production within the current application (Cadence) must be available on the new platform.

## Key Concept
This is a migration requirement — ensuring feature parity. Every rule, element, and configuration currently active in Cadence must be available in CRR 2.0. However, the migration strategy is deliberately NOT a lift-and-shift.

## Migration Strategy (Confirmed from Coaching)

### Deliberate Manual Re-Configuration (No Lift-and-Shift)
- **Strategic decision:** Users manually configure all risk elements in CRR 2.0 for the first time
- **Rationale:** Acts as a **quality gate** — every element, rule, and weight is physically reviewed and validated through the new UI
- Avoids carrying over legacy baggage, errors, or outdated configurations
- Simultaneous UI testing and product validation by actual users
- Slower initially, but ensures data quality and user familiarity with new platform

### Exception: FA Questionnaire (Backend Migration)
- Fundamental Assessment questionnaire framework (fixed structure of questions/answers) was migrated via backend
- FA structure is fixed — users only update answers and comments, not the framework itself
- Logical exception: no value in manually recreating a standardized, unchanging structure

### Data Model Architecture Change

**Cadence (Legacy) — Siloed Per-Market Assessments:**
```
Market A → Assessment ID 1 (all rules for Market A)
Market B → Assessment ID 2 (all rules for Market B)
...40+ separate assessment IDs (siloed, duplicated)
```

**CRR 2.0 — Single Assessment with Element-Level Scope:**
```
Single CRR Assessment (all markets)
└── Risk Elements (enterprise-shared by default)
    └── Scope at element level (not assessment level)
        └── Localization on edit (copy-on-write per market)
```

### Key Architecture Decisions
1. **Single CRR assessment** replaces 40+ siloed assessment IDs
2. **Scope moved to risk element level** — markets inherit enterprise elements by default
3. **Localization on edit:** When any property (rule, weight, market setting) is edited, the risk element is **localized for that market** (copy-on-write pattern)
4. **Enterprise propagation:** Changes to enterprise elements automatically cascade to all markets that haven't localized

### Why This Architecture
| Aspect | Cadence (Siloed) | CRR 2.0 (Single + Localize) |
|--------|-----------------|---------------------------|
| Enterprise consistency | No shared baseline | Enterprise elements shared by default |
| Market customization | Full duplication per market | Edit-triggered localization only |
| Scalability | New market = copy entire assessment | New market = inherits enterprise |
| Rule duplication | Same rule duplicated 40+ times | One enterprise rule, localized where needed |
| Maintenance | Update 40+ copies for changes | Update once, auto-propagates |

### Connection to Asset Manager
This element-level copy-on-write architecture directly mirrors the **Asset Manager copy-on-write pattern** — both implement market autonomy + enterprise governance through the same localization-on-edit principle.

## Discovery Questions (Answered)
- **1:1 migration of legacy rules?** → NO. Manual re-configuration by users (quality gate strategy). Not lift-and-shift.
- **Deprecated elements excluded?** → Yes, users only configure what's actively needed. Legacy baggage is not carried over.
