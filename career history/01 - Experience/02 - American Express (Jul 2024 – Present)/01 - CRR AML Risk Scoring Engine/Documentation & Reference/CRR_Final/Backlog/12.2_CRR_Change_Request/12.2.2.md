# Sub-Requirement: 12.2.2

**Parent Capability:** [CRR Change Request](12.2_Capability.md)

## Description
The access to the Change Request UI and the capabilities within (submit/review/disposition) should be based on permissions.


## Discovery Questions
- [ ] Does a Change Request need its own approval workflow separate from the Sandbox approval?
- [ ] Can one Change Request span multiple markets?

## Development Status

**Status:** No
**Comments:** Features related to IAM/Permissions are not yet implemented.


## System Behavior & User Journey

**System Behavior:** Identity and Access Management (IAM) is handled via the enterprise Identity Provider (IDP). The application enforces Role-Based Access Control (RBAC). Roles (e.g., 'Analyst', 'Approver', 'Admin') are mapped to specific API endpoints and UI components. This ensures users only see/edit what they are entitled to.

**User Journey:** User logs in -> System validates Token -> Fetches Permissions -> UI renders enabled/disabled buttons based on permission set.


## Business Questions (Mom Test)

These questions are designed to reveal hidden desires and operational realities:

- What is the single most expensive mistake a user could make here?
- How do you currently solve this problem manually (Excel? Email?)?
- Who is the one person who should *never* have access to this?
