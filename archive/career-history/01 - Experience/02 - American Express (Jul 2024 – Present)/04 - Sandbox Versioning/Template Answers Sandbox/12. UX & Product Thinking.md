## Q12. UX & Product Thinking

**What are the key UX principles guiding the sandbox design?**

Principle 1: Clarity of state. Sandbox state (Draft, Submitted, Approved, Promoted, Rejected) is always visible. User always knows "where am I in the workflow?" Principle 2: Progressive disclosure. On first view, show creation button only. After creation, progressively reveal edit tabs, submit button, approval status. Reduce cognitive load. Principle 3: Prevention of loss. Exit-blocking modals when user navigates away with unsaved changes. Example: "You have unsaved edits in Rules. Save or discard?" Principle 4: Audit transparency. Every action (edit, submit, approve) logged and visible in timeline view. Users understand history and can verify compliance. Principle 5: Error prevention. Before Submit, modal summarizes all changes and requires justification. User sees "Are you sure?" before crossing the Rubicon.

**How do you design the UI for analysts with low technical fluency?**

Simplicity through domain-specific language. Don't say "commit" (git term); say "Submit for Simulation" (domain language). Don't show system messages ("Exception: ReferenceError"); show user-friendly errors ("Asset 'US Market Default' not found in production. Edit or select a different asset."). Use visual affordances: button states (disabled Submit if no changes), color coding (Green = Approved, Yellow = Pending, Red = Rejected), icons (checkmark = ready to promote, X = requires action). Progressive disclosure: novice analysts see simple workflows; experienced analysts see advanced options (e.g., simulation cancel, rollback to specific version).

**How do you handle error scenarios and edge cases?**

Edge case 1: User submits sandbox, then leaves without reviewing simulation results. Modal on exit: "Simulation completed. Results pending your review. Leave anyway?" Edge case 2: User approves sandbox, then realizes there's an error. Too late—already approved. Transition: Approved → Rejected (allow rejecter to add comments, allowing rework). Edge case 3: Two users both create Enterprise sandboxes simultaneously. System message: "Enterprise sandbox already exists. Wait for other user to finish or delete theirs." Edge case 4: Simulation times out. Retry button visible. User can retry simulation or proceed with best-effort approval based on prior simulation data. All edge cases are handled gracefully with clear user guidance.

**How do you make approval workflows efficient?**

Approval SLA challenge: two-step approval can be slow. Optimizations: (a) Pre-approval: first approver and alternate first approver both visible in sandbox detail view—allows parallel preparation, (b) Approval summary: show only the essential info (what changed, why, simulation results delta) on approval screen—reduce time to decide, (c) Rejection shortcuts: if first approver rejects, user can re-edit in Draft without full rework, (d) Escalation: if approval pending >4 hours, auto-notify manager for escalation. Together, these reduce approval cycle time to <2 hours for typical changes.

**How do you design for audit trail usability?**

Audit trail export is a CSV with columns: Timestamp | User | Action | Object (Rules/Assets/FA) | Details | Justification | Approval Status. For compliance examiners, this is instantly reviewable and filter-able (e.g., "Show me all Rule changes by User X in last 90 days"). Alternative view: timeline on sandbox detail screen showing action sequence. Example: "2024-01-15 10:00 - Alice created sandbox. 2024-01-15 10:15 - Alice edited Rules. 2024-01-15 10:30 - Bob submitted for simulation. 2024-01-15 11:00 - Simulation complete. 2024-01-15 11:10 - Charlie approved. 2024-01-15 11:20 - Dave approved. 2024-01-15 11:25 - Promoted to production." This narrative format is intuitive for non-technical stakeholders.

**How do you minimize cognitive load for analysts reviewing simulation results?**

Simulation results can be overwhelming: thousands of customer cohorts, risk score deltas for each. Simplification: (a) dashboard view showing aggregate metrics (X% of customers moved from Medium to High risk; average score delta = +2.5), (b) sortable table of affected customer cohorts (filter by delta magnitude, status), (c) drill-down: click a cohort to see individual customers and their score changes, (d) export results CSV for advanced analysis. Defaults show summary; power users can drill down.
