## Q13. Failure Mode Analysis

**What are the top 3 failure modes, and how do you mitigate each?**

Failure Mode 1: Simulation times out or fails. Impact: analyst cannot review results before approval; approval becomes a guess. Regulatory risk: BRD 12.8 (simulation capability) unmet. Mitigation: (a) set SLA [VERIFY: add target, likely <5 min]; monitor actual latency; if trend is bad, escalate to GCP team for optimization, (b) allow retry (non-blocking), (c) allow proceeding with prior simulation data or skipping simulation for expedited changes (rare, approval comment required), (d) alert monitoring: if >X% of simulations fail per week, page on-call engineer. Test coverage: load test with [VERIFY: add customer population size] customers; verify SLA is met.

Failure Mode 2: Atomic promotion transaction fails (e.g., Rules commit succeeds, Assets commit fails). Impact: inconsistent state; customer scoring is broken. Regulatory risk: BRD 12.10 (atomic change) violated; audit trail shows partial state. Mitigation: (a) pre-promotion validation: before committing, run comprehensive checks (schema, referential integrity, simulation on new config); only proceed if all checks pass, (b) transaction rollback: database transaction is Serializable; if any component fails, entire transaction rolls back—no partial state, (c) post-promotion verification: immediately after promotion, run smoke test (rescore sample customers with new config); if smoke test fails, auto-trigger rollback, (d) communication: if rollback occurs, user sees modal "Promotion failed. Rolled back to prior version. Contact support with code X for analysis." Alert monitoring: zero tolerance for partial promotions.

Failure Mode 3: Approver A approves, but later realizes change is risky; Approver B approves anyway. Impact: bad config reaches production. Regulatory risk: two-step approval is rubber-stamped (defeats the control). Mitigation: (a) rejection workflow: if Approver A has buyer's remorse, they can revoke approval (Approved → Draft, allowing Submitter to rework), (b) comment section: Approver A can add comment "I approve but with concerns about X" visible to Approver B, (c) escalation: complex changes require both Approver A and Manager sign-off, not just two analysts, (d) training: emphasize that approval is not rubber-stamp; it's decision-making on risk, (e) monitoring: post-launch, audit approvals; if same approver pair consistently approves without reviewing, escalate to management.

**What are secondary failure modes?**

Failure Mode 4: User deletes a sandbox by mistake. Impact: loss of work. Mitigation: soft delete (mark as deleted, allow undelete within 24 hours). Permanent delete requires confirmation modal. Failure Mode 5: Concurrent edits within a sandbox (User A and User B both trying to edit Rules). Mitigation: pessimistic locking. User B sees "Sandbox locked by User A (since 10:00 AM). Estimated wait time: 15 min. Force unlock? [risky button]" Failure Mode 6: Audit trail becomes corrupted or incomplete. Mitigation: database constraints ensure audit trail integrity (no deletion allowed, only append). Backup audit logs to immutable storage (S3) weekly. Failure Mode 7: Simulation results don't match production results after promotion. Impact: simulation is unreliable; erodes user trust. Mitigation: post-promotion reconciliation job runs 24 hours after promotion, comparing simulated scores to actual production scores; alerts if delta >threshold ([VERIFY: add threshold, likely 5-10%]).

**How do you handle rollback failures?**

Rollback should succeed 100% of the time—it's a critical recovery mechanism. Design: Rollback doesn't recompute; it loads a prior version from version history (metadata operation). If rollback fails, it's a system-level failure (database corruption). Mitigation: (a) version history is replicated across multiple regions; if primary fails, failover to replica, (b) periodic validation: weekly, integrity check on version history (checksum all versions; alert if mismatch), (c) alert: if any rollback fails, page entire on-call team. This is SLA 100% success rate.

**How do you test these failure scenarios?**

Testing approach: chaos engineering. Inject failures in staging: kill GCP connection, trigger database constraint violations, simulate slow queries, trigger network partitions. Observe: does system gracefully degrade? Do users see helpful errors? Can they recover? Run these tests weekly in staging. Pre-launch: execute comprehensive failure scenario test matrix in UAT covering all modes above.
