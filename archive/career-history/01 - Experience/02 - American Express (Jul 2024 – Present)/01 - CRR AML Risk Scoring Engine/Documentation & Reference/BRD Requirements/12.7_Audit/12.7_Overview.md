# 12.7 Audit on the CRR Engine

**BRD Ref:** 12.7
**Status:** Yes (tracks changes pushed to Production)
**Beads Task:** career-context-2zu

## Business Requirement
System should be able to keep track of all updates made to the CRR framework and reference lists.

## Purpose
System capability to track all updates (what/who/when/why).

## Outcome
Comprehensive tracking of all changes for audit and reporting purposes.

## Implementation (from Coaching)

### How Audit Works in CRR 2.0:
- **History tab** in sandbox UI shows version history, status changes, who/when/comments
- Every sandbox lifecycle event is tracked: creation, edits, submission, simulation, approval, rejection, production merge
- **Audit History** is one of the core CRR capabilities personally defined by PM

### What is Tracked:
| Sub-Req | What Gets Tracked | Mechanism |
|---------|-------------------|-----------|
| 12.7.1 | Changes to Lists, Risk Elements, Risk Categories (weight/multiplier add/modify/delete) | Sandbox history + production merge logs |
| 12.7.2 | Version history at enterprise/market/legal entity level | CRR version uplift on each production push |
| 12.7.3 | Changes to FA, Notable Lists, reference data | Unified sandbox — FA/Asset changes tracked alongside rule changes |
| 12.7.4 | Overrides to FA/Notable List reference data | Same audit trail mechanism |

### Reporting Connection:
- **R13:** FA/Centralized Lists/Notable Lists changes report (who, when, what changed)
- **R14:** Audit trail for all risk points changes per customer (user, timestamp, status, comments)
