# 12.3.2 — Permission-Based Updates

**Parent:** 12.3 CRR Updates
**Status:** Not Started (IAM blocking)

## Requirement
The ability to make updates should be based on user permissions (configurable).

## Current User Model (Confirmed from Coaching)

| User Type | CRR Tab | Sandbox Tab | Asset Manager | FA | Reporting | Alerts |
|-----------|---------|-------------|---------------|-----|-----------|--------|
| MCO / FIU | Read-only (own market only) | No access | Read-only | Read-only | TBD | TBD |
| CRR Business User | Read-only | Full edit access | Edit (inside sandbox) | Edit (inside sandbox) | TBD | TBD |

### Key Permission Boundaries:
- MCO sees only their market's effective config (localized element priority over enterprise)
- CRR Business Users edit only inside sandbox — never directly in production
- 2-step approval requires different users for step 1 and step 2
- Enterprise concept hidden from MCOs — they see "what applies to me" not "where it came from"

## What 12.3.2 Aims to Build
- Configurable RBAC for update capabilities
- Granular permissions: who can create sandbox, who can edit, who can submit, who can approve
- Integration with enterprise IAM/IDP
- Currently blocked by IAM infrastructure readiness (same blocker as 12.2.2)

## Interview Notes
- IAM is a cross-cutting blocker affecting 12.2.2 and 12.3.2
- Current user model is informally enforced through application-level access control
- Formal RBAC integration planned but dependent on enterprise IAM readiness
