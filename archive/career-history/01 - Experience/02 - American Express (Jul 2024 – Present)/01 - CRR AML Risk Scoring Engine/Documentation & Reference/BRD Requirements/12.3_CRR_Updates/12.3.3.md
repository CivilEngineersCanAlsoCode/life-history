# 12.3.3 — Data Point Combination with Constraints

**Parent:** 12.3 CRR Updates
**Status:** Missing constraint/warning logic

## Requirement
System should allow for combining multiple data points to create risk elements (e.g., Country + Industry).
- User must be able to combine two or more available data points to create/update a risk element
- System should throw a warning immediately if there is a constraint in creating or updating the risk element

## Confirmed Details (from Coaching)

### Data Point Rules:
- Data points are **pre-defined** — user cannot create new data points
- User selects from available data points when building rule conditions within a ruleset
- Multiple data points can be combined using AND/OR operators (Basic mode = AND only; Advanced mode = AND + OR + parentheses)

### Constraint Enforcement — 3 Ratio Rule Types:
The restrictions apply specifically to **ratio rules** — there are exactly 3 types:

| Ratio Rule Type | Description |
|----------------|-------------|
| **Income Type Ratio** | Ratio based on income type data points |
| **Income Count Ratio** | Ratio based on income count data points |
| **Transaction Ratio** | Ratio based on transaction data points |

**Constraint:** Within these ratio rules, **two aggregation-type data points cannot coexist** in the same rule. This is because aggregation data points (SUM, COUNT, etc.) cannot be meaningfully combined in a ratio calculation.

- Restriction is enforced at the **UI level** — UI limits available values to prevent invalid combinations
- No backend validation needed — UI prevents the condition from being created in the first place

### Current Status:
- Data point combination itself works (In Development)
- **Missing:** Constraint warning logic — system should throw a warning when user attempts an invalid combination
- Current approach: UI silently prevents invalid combinations by limiting dropdown values
- BRD asks for explicit warning/feedback to user explaining WHY a combination is not allowed

## Design Consideration
UI-level enforcement is simpler but less transparent. BRD requirement asks for explicit constraint warnings so users understand why certain combinations are blocked — this is the gap that needs to be filled.

## Interview Notes
- Only 3 exceptional restriction scenarios — not a broad constraint system
- Aggregation type incompatibility is the root cause of restrictions
- UI-based enforcement confirmed (not API-level validation)
